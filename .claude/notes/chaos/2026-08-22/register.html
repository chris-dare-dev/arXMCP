Theme 01 · the shipped artifact

The app cannot succeed on first run, and cannot say so

Three findings compose into a single fact. A user who double-clicks arXMCP.app today gets nothing at all — and no way to find out why.

CHAOS-PKG-02There is no first-run state that can succeed

The self-authored launch plan points the data root at an empty ~/Library/Application Support/arXMCP, and the bundle ships no ingest path. The child always raises CorpusNotIngestedError: corpus-version.json not found. The remedy its own error names — make up-wizard — does not exist inside a bundle.

CHAOS-PKG-01The failure is completely invisible

tauri.conf.json declares app.windows: [], and every fail() path is eprintln! followed by exit. No window, no dialog, no Dock icon; open itself exits 0. The process dies in five to seven seconds. The only trace is an NDJSON file under ~/Library/Application Support/arXMCP/logs/. Corroborated independently by the supervisor lane as CHAOS-SUP-07 and CHAOS-SUP-11.

CHAOS-SUP-10The one diagnostic destroys itself

logs/desktop-child.log is truncated on every launch. The second double-click erases the evidence from the first.

These are not independent bugs to be ranked against each other. Fixing the corpus bootstrap without fixing the silence leaves the next failure equally undiagnosable; fixing the silence alone produces a well-reported permanent failure. Both halves are load-bearing.

Theme 02 · the interface

The UI's entire error layer is dead code

This is the highest-leverage frontend fix on the board, and it is one line. The application's own Content-Security-Policy at server/middleware.py:172 sets script-src 'self' 'unsafe-inline' — with no 'unsafe-eval'. htmx implements hx-on:: through new Function(), which requires it. Every page load throws:

EvalError: Evaluating a string as JavaScript violates the following
Content Security Policy directive        htmx.min.js:2:44684

That kills all twelve hx-on:: handlers — seven hx-on::response-error and five hx-on::after-request, counted across index.html (3) and notebook_detail.html (9). The UI detects its errors correctly and then silently drops them on the floor. CHAOS-FE-02 (a 422 or 409 on notebook create displays nothing whatsoever) is a direct consequence.

CHAOS-FE-03The CSP fix does not cover backend death

After kill -9 on the server, the status badge holds its stale pre-kill value, no offline banner appears, and every control silently no-ops. Restoring the CSP will not repair this: htmx emits htmx:sendError for connection failures, and no handler listens for that event at all. It needs to be written.

Theme 03 · the trust boundary

The containment story is inverted

apps/desktop/README.md documents a careful payload-containment model: resolve_inside, symlink refusal, component-wise containment, a digest check before the child is trusted. All of it is real, and all of it is reachable only from the self-authored arm.

CHAOS-PKG-06The environment launch-plan arm applies no containment

When ARXMCP_DESKTOP_LAUNCH_PLAN is set, load_plan at main.rs:143-158 performs fs::read → serde_json → validate_plan → return. It never calls child_payload_candidates or resolve_inside. Demonstrated by executing /usr/bin/touch with attacker-chosen arguments against the signed release bundle. Found independently by the supervisor lane as CHAOS-SUP-03, which also confirms the seam ships enabled in the signed .app.

The comment at main.rs:145 reads: “The self-authored plan is NOT trusted more than an external one.” True, and backwards. The external plan is trusted more — it skips the containment the self-authored arm submits to.

CHAOS-PKG-07The identity digest is not a tamper check

lifecycle.rs:109 hashes plan.identity_file, and the crate's own unit test at main.rs:892 asserts identity_file == child_argv[0]. It hashes the file it is about to execute — self-consistency, not integrity.

CHAOS-PKG-08Nothing verifies the seal at launch

A one-byte flip in the signed child Mach-O still executes. codesign catches every tamper tested; nothing runs codesign at runtime. The 5,300-file payload has no launch-time integrity check.

Theme 04 · the data layer

Failures a user cannot distinguish from working software

CHAOS-DATA-01A destroyed corpus still boots READY

Zero or truncate every LanceDB data fragment and the table still opens, count_rows() still returns the full 4,279 (fragment metadata only), and the health path reports DegradedState=None. The server comes up healthy on a corpus that cannot answer a single query; only the first real search raises. A one-row smoke read at startup catches every case tested.

CHAOS-DATA-02The divergence alarm is permanently ringing

The shipped var/arxmcp/index/lancedb-staging marker claims chunk_count: 105 / paper_count: 1 against a table holding 4,279 rows. At the 5% tolerance that corpus reports degraded(chunk_count_diverged) on every single boot — desensitising the one signal that would surface a real divergence.

CHAOS-DATA-03A damaged cache file is fatal to startup

A corrupt, truncated, read-only, directory-shaped or externally-locked Tier-1 cache DB kills both startup and the post-ingest corpus rebind. RetrievalCache.open is called bare at server/resources.py:868 and :1142, directly contradicting the contract written at server/cache_sqlite.py:28-31 — “fall through to recompute; log; alert”.

One quieter sibling deserves attention: CHAOS-DATA-05 — the marker's embedder_version is never compared against the loaded model, so swapping the embedder yields silent wrong-vector-space retrieval with no warning anywhere.

Verified clean

What held up under attack

Recorded deliberately, so a later run can tell tested-and-clean from never-looked-at. The server itself is genuinely well hardened; the defects cluster in the desktop shell, the packaging, and the data layer.

  • XSS and template injection — clean. Jinja autoescape verified empirically and statically. Zero |safe, zero Markup(, every f-string fragment html.escaped.
  • Path traversal — clean. 404 on all seven encodings, against /static/ and against slugs that become paths.
  • Server robustness — clean. 200-concurrent load, slowloris, chunked overflow, malformed JSON, config hostility and SIGTERM drain produced no crashes, hangs, 500s or orphans. CSRF and DNS-rebind are properly defended (Origin 403 / Host 421 / Sec-Fetch-Site 403). The startup token is compared with hmac.compare_digest.
  • Contract-frame fuzzing — clean. All 17 mutations rejected within bounds, including a depth bomb, a missing terminal LF, and concatenated frames.
  • Restart storm — clean. Ten rapid start/quit cycles leaked no file descriptors, temp directories, ports or processes.
  • Identifier collisions — clean. No reachable paper_id flatten collision; old-style slashed ids resolve distinctly.
  • Bundle determinism — clean. Both assembly-report.json claims verified against the artifact with no drift, and a symlinked payload root is refused rather than silently traded for the other layout.

Known unknowns

Coverage gaps — untested, not clean

  • MCP handler-level input validation. Bootstrap mode short-circuits every tool to a stub envelope before the handler runs, so traversal, NUL and injection tests in paper_id and chunk_id never reached real code. Validation there is handler-level rather than schema-level, so hostile ids do pass the JSON-schema gate. Logged as CHAOS-API-11; closing it needs a re-run against a live corpus.
  • The populated-corpus UI. Notebook LanceDB directories are empty on this checkout, so every populated search path in the frontend went unexercised.
  • Dry-run write honesty. NOTEBOOKS_BASE resolves at import from ApplicationPaths, so redirecting it required either writing under var/arxmcp/ or editing tools/ — both forbidden by the run's safety rules. Separately: notebook_ingest.py and notebook_pdf_parse.py have no --dry-run at all.
  • BM25/dense skew, disk pressure, model failure modes, freshness mtimes. Timeboxed out of the data lane. BM25 skew is the highest-value next target — the index is 18 MB and trivially cloneable.
  • Read-only volume launch and the Info.plist arms. LaunchServices caching confounded both; recorded as info lines rather than implied clean.

Corrections

Two pieces of prior project knowledge were wrong

  • The “3-calls-per-session limit” does not exist. The real caps are 30 for search_papers and 100 for get_chunk. The boundary is exact — the 30th passes, the 31st returns a clean RETRIEVAL_CAP_REACHED envelope with no stack trace. The new-session-per-call bypass is real and marked deliberately non-security in server/session.py.
  • A second documented bypass is unreachable. The docstring at server/session.py:24-31 claims that omitting Mcp-Session-Id skips cap enforcement. The MCP layer returns 400 first. Logged as CHAOS-API-07.

Recommended sequence

Fix order

Ordered by what unblocks the most downstream work, not strictly by severity.

  1. Make the bundle able to start, and able to complain. CHAOS-PKG-02 plus CHAOS-PKG-01 — a first-run path that can succeed, and a window or NSAlert that can report when it does not. Everything else is undiagnosable until this lands.
  2. Restore the UI error layer. CHAOS-FE-01 — one CSP line brings back twelve handlers. Then add the htmx:sendError listener that CHAOS-FE-03 needs, since the CSP fix alone will not cover it.
  3. Close the containment inversion. CHAOS-PKG-06 — either apply resolve_inside and the payload-root check to the environment arm, or compile that arm out of release builds entirely.
  4. Make READY mean answerable. CHAOS-DATA-01 — a one-row smoke read at startup, and reconcile the shipped marker in CHAOS-DATA-02 so the divergence alarm stops crying wolf.
  5. Add lifecycle watchdogs. CHAOS-SUP-06 (no child-death detection in production mode) and CHAOS-SUP-05 (a SIGSTOP'd child hangs the supervisor for 281 seconds with zero events).
