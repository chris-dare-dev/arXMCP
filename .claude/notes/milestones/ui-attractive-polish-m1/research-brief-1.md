## External sources

**MDN `prefers-reduced-motion`** — Baseline 2020, widely available. The
`*, *::before, *::after` selector inside the media query is the established pattern
(used by normalize.css, Tailwind, and Bootstrap). The `!important` markers inside
the block are load-bearing per the intent (override UA defaults).

**MDN `:focus-visible`** — Baseline 2022. The `:focus:not(:focus-visible)` reset
for mouse users is the correct pattern; it suppresses the outline for mouse/touch
without removing it for keyboard. Safari ≥15.4 supports `:focus-visible`; the
project's existing `vendor`-prefix strategy is none (no preprocessor) — this is safe.
Known caveat: some Safari versions ≤15.3 may not support `:focus-visible` and fall
through to `:focus` — acceptable degradation (they get the outline for all input
modes rather than none for mouse).

**WAI-ARIA `aria-live` + `aria-atomic`** — `aria-live="polite"` causes SR to announce
changes after the current speech finishes. `aria-atomic="true"` instructs the SR to
announce the entire region as one string when any part changes. For the 10s badge
poll, `aria-atomic="true"` is correct — without it, SR may announce only the CHANGED
portion (e.g. the corpus version number), which is confusing. The AC VoiceOver test
("announces as one atomic string") validates this directly.

**htmx 2.0.10** (vendored at `frontend/static/htmx.min.js`) — applies
`htmx-settling` and `htmx-swapping` CSS classes during swaps. These are NOT on the
live region target itself — they are on the element being replaced (for `outerHTML`)
or its parent (for `beforeend`). The `aria-live` announcement fires when the DOM
mutation completes; htmx settling classes do not interfere with ARIA mutation
observers. No interaction risk.

**WebAIM G1 (skip link technique)** — canonical pattern: visually hide off-screen
with `position: absolute; left: -10000px`, reveal on `:focus-visible` with
`left: 1rem; top: 1rem`. The AC specifies `background: var(--accent); color: #fff`
for the revealed state. The `tabindex="-1"` on `<main>` is required for
`window.location.hash` navigation to work in all browsers (clicking the skip link
or activating it via Enter moves focus to `<main>`; without `tabindex="-1"`, some
browsers silently ignore the focus target).

## Recommendation

**Implement UPL-1, UPL-2, UPL-4 as pure CSS additions to `app.css`; implement
UPL-3 as HTML attribute additions to templates AND as parallel f-string updates
in `server/routes/ui.py` and `server/routes/notebooks.py` for the outerHTML-swap
fragments.**

The CSS changes are straightforward and low-risk. The implementation trap is
UPL-3: the two elements using `hx-swap="outerHTML"` (`#status-badge` and
`#display-name-block`) regenerate from Python f-strings, not templates — if the
implementer only updates the templates, the attributes will vanish after the first
htmx poll. Fix all four locations in one commit.

Ordering within the implementation session: UPL-4 (skip-link CSS + template edit)
first since it is structurally isolated; then UPL-2 (focus-visible CSS); then
UPL-1 (reduced-motion block); then UPL-3 (aria-live attributes + f-string updates).
Run `make test` after each UPL to catch regressions early.

The line-count budget (≤165 lines for app.css after m1) is achievable: current
126 lines + ~8 (UPL-1) + ~10 (UPL-2) + ~7 (UPL-4 skip-link) = ~151.

## Open questions

**(a) UPL-1 `*, *::before, *::after` selector interaction with existing transitions.**
Confirmed: the current `app.css` has ZERO `transition` or `animation` declarations.
The universal clamp block is safe and will not affect any existing behavior.
No action required — the implementer can proceed directly.

**(b) `button.danger:focus-visible` outline color.**
The roadmap AC explicitly resolves this: `outline-color: var(--danger)`. The challenger
finding ("destructive controls deserve the LOUDEST focus ring, not the quietest")
is already incorporated into the AC. Use `var(--danger)`. No decision needed.

**(c) `aria-live` on `#status-badge` causing VoiceOver over-announcement on 10s poll.**
This is a real concern but `aria-atomic="true"` is the mitigation — it announces the
full badge string once per poll cycle, not per character. The AC VoiceOver smoke-test
is the evidence gate. The implementer must test this manually; if VoiceOver over-
announces, the fallback is `aria-relevant="text"` (only text-content changes, not
attribute changes). This is the one item that requires human VoiceOver verification
before the milestone can be marked complete — it cannot be automated.

**(d) `tabindex="-1"` on `<main>` keyboard-trap regression.**
`tabindex="-1"` makes an element programmatically focusable but NOT Tab-traversable.
No keyboard trap is introduced — Tab will not stop at `<main>`. This is safe.
No action required.

**(e) outerHTML-swap aria-live persistence — the key implementation risk.**
NOT an open question — the implementer MUST update:
1. `frontend/templates/base.html` line 65 (`#status-badge` initial render)
2. `server/routes/ui.py:261-264` (`get_status_badge` f-string fragment)
3. `frontend/templates/notebook_detail.html` line 15 (`#display-name-block` initial render)
4. `server/routes/notebooks.py::_display_name_fragment` (f-string fragment)
5. `frontend/templates/notebook_detail.html` line 161 (`#ingest-status` initial render)
6. Verify ingest-status fragment generators in `notebooks.py` for the polling fragments

Items 5-6: `#ingest-status` uses `hx-swap="outerHTML"` on its initial placeholder,
but the polling fragments also use `hx-swap="outerHTML"`. Check every ingest-status
fragment generator in `server/routes/notebooks.py` — the aria-live attribute must
appear on EVERY fragment, not just the initial placeholder.

No open questions remain that block implementation. The implementer can proceed
on the above recommendation.
