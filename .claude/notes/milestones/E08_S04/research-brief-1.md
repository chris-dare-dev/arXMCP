# E08_S04 Research Brief 1 — Tool-use ID canonicalization and hard retrieval caps

## 1. In-codebase context

### Design constitution — load-bearing constraints

**`07-multi-agent-caching.md` lines 87–117 (the canonicalization rule)**:

```
Anthropic's API assigns server-side `id` fields to `tool_use` and `tool_result`
content blocks (e.g. `toolu_01Abc...`). These IDs are **non-deterministic across
calls**. As soon as one tool call happens in agent A and a different one happens
in agent B, the prefix between them diverges and downstream cache reuse dies.

**Mitigation:** the orchestrator (the layer that composes sub-agent prompts) must
**normalize tool-use/tool-result IDs to deterministic values** before composing
the next agent turn.

def canonicalize_turn(messages):
    counter = 0
    id_map = {}
    for msg in messages:
        for block in msg.get("content", []):
            if block.get("type") in ("tool_use", "tool_result"):
                old_id = block.get("id") or block.get("tool_use_id")
                if old_id not in id_map:
                    id_map[old_id] = f"toolu_{counter:08d}"
                    counter += 1
                if "id" in block:
                    block["id"] = id_map[old_id]
                if "tool_use_id" in block:
                    block["tool_use_id"] = id_map[old_id]
    return messages
```

And at line 117: **"This is the single most underrated optimization in agentic pipelines."**

**`07-multi-agent-caching.md` line 5**: "Get this right and 4-agent fan-out is nearly free; get it wrong and 4 agents cost you 4× everything."

**`07-multi-agent-caching.md` lines 65–82 (BP placement — direct constraint for E08_S04)**:

> BP3 is **dropped**. Slots 3–4 are reserved for future use.

This means the call site for `canonicalize_turn` must compose into BP1/BP2 only; it must NOT attempt a BP3 injection.

**`06-mcp-server-design.md` line 40**:

> "`Mcp-Session-Id` header is globally unique and cryptographically secure. Used for our **per-session rate limits** and observability."

This is the design constitution's explicit statement that the session-id keys per-session state such as retrieval caps.

### Existing server structure

**`server/middleware.py`** — Security-hardening ASGI middleware, pure-ASGI pattern (no `BaseHTTPMiddleware`). Defines `OriginValidationMiddleware`, `HostValidationMiddleware`, `SecurityHeadersMiddleware`, `RequestBodySizeLimitMiddleware`. Crucially: **does NOT handle `Mcp-Session-Id` in any way**. The session-ID is generated by the MCP library's `StreamableHTTPSessionManager` (confirmed via `.venv` source: `new_session_id = uuid4().hex` at `streamable_http_manager.py:244`). The server is responsible only for CONSUMING the session-id — the MCP library creates it.

**`server/main.py`** — ASGI middleware stack is add-in-LIFO order; SecurityHeaders wraps everything. The `/mcp` path is exempt from `BodySizeCapMiddleware`. There is no existing session-state tracking at the middleware layer.

**`server/handlers/search.py`** — `handle_search_papers` is a plain async function; it has no access to request headers or session context. It receives only typed Python arguments (`query`, `level`, `k`, `filters`, `cursor`). There is no injection point for `Mcp-Session-Id` at the handler level via the current FastMCP `add_tool` pattern.

**`server/handlers/chunk.py`** — Same pattern. No access to session context.

**`server/tools.py`** — `register_all` uses `mcp_server.add_tool(handler, name=..., description=..., meta=...)`. FastMCP handler signature is typed; no session-context parameter in the current call.

**`server/orchestrator/`** — **Does not exist.** Confirmed: `ls server/orchestrator/` returns "NO orchestrator dir". This is a net-new package.

### Error propagation pattern

From `tests/test_tools_all.py` lines 373–397: When a handler raises `ValueError`, FastMCP wraps it into a JSON-RPC error OR a `CallToolResult(isError=True)`. The test accepts either shape:

```python
assert body.get("error") is not None or body.get("result", {}).get("isError") is True
```

`CallToolResult` has an `isError: bool = False` field confirmed via `.venv` inspection. The `RETRIEVAL_CAP_REACHED` error must follow one of these two patterns. The existing pattern in the codebase is: handler raises `ValueError` → FastMCP wraps → `isError=True`. The brief says "structured error with code `RETRIEVAL_CAP_REACHED`" — this implies returning `CallToolResult(content=[TextContent(...)], isError=True)` directly rather than raising.

### The MCP session-ID — server-generated, not client-supplied

From `.venv/lib/.../mcp/server/streamable_http_manager.py:244`:
```python
new_session_id = uuid4().hex
```
The server generates the session ID. The pattern is `SESSION_ID_PATTERN = re.compile(r"^[\x21-\x7E]+$")` — printable ASCII only. The `Mcp-Session-Id` header is echoed back in the response and subsequent requests from the client carry it to route to the same `StreamableHTTPServerTransport` instance. This means the `SessionState` can be keyed by this server-generated UUID hex — there is no risk of client-supplied spoofing at the session routing level (the `StreamableHTTPSessionManager` validates it before dispatch).

**How middleware gets the session-id**: the ASGI `scope["headers"]` contains `mcp-session-id` on requests after session initialization. Pure-ASGI middleware can extract it from headers before forwarding to the app. However, the header is set by the MCP library in the response — the request from the client carries it on all subsequent calls after the `initialize` handshake. On the first `initialize` call, there is no session-id in the request.

## 2. Prior decisions and lessons

### E06_S05 security middleware lessons

The E06_S05 middleware module's docstring explicitly states:
> "The ``BaseHTTPMiddleware`` form was shown in E06_S01 to silently no-op response interception ... All three are pure-ASGI (not `BaseHTTPMiddleware`)."

**Lesson**: any new `SessionStateMiddleware` MUST be pure-ASGI, not `BaseHTTPMiddleware`. This is a hard project rule established in E06_S01 F1.

### E08_S02 integration seam note

E08_S02's implementation summary explicitly flags:
> "The orchestrator imports `ROLE_PREFIXES` and composes the messages-API request body..."

This suggests the orchestrator is expected to be a distinct module (E08_S05 likely) and E08_S04's `id_canon.py` is a utility the orchestrator will call — not the orchestrator itself.

### E08_S03 resources pattern

`server/session.py` does not exist. Per E08_S03, session-level state is NOT currently tracked. The retrieval cache is process-scoped (not session-scoped). E08_S04 introduces the first per-session state. The pattern for process-level singletons in this codebase: module-level variable + `get_X()` / `set_X()` functions (see `server/cache.py`, `server/tools.py`). For per-session state, the analog is a dict keyed by session-id managed in a module-level `_sessions: dict[str, SessionState]`.

### MCP spec on Mcp-Session-Id semantics

Per the `mcp` library source (`streamable_http_manager.py:228-253`): the session-id is per MCP connection lifecycle (initialize → terminate). All tool calls within that connection share the same session-id. This matches the brief's intent: cap `search_papers` at 3 rounds and `get_chunk` at 4 materializations per MCP session.

**The server generates the ID, not the client.** Client cannot override or spoof it to bypass caps (the session manager validates inbound session-ids against its own registry).

### "Things that always break" — F1 warning from E06_S01

E06_S01 F1: `BaseHTTPMiddleware` silently no-ops response interception. E06_S05's fix is the canonical template for new middleware. The cap enforcement middleware MUST follow the `RequestBodySizeLimitMiddleware` / `OriginValidationMiddleware` pure-ASGI pattern.

## 3. External sources

The MCP 2025-06-18 spec at `https://modelcontextprotocol.io/specification/2025-06-18` was not fetched directly (network access not attempted in this research pass), but the `.venv` library source is authoritative. Key confirmed facts:

- `Mcp-Session-Id` is server-generated via `uuid4().hex` — not client-supplied.
- The session lifecycle is: `initialize` (no session-id in request, server generates and returns it) → subsequent requests carry it → `DELETE /mcp` terminates.
- The `SESSION_ID_PATTERN` is `^[\x21-\x7E]+$` — UUID hex satisfies this.
- The `StreamableHTTPSessionManager` routes by session-id; a new session-id means a new `StreamableHTTPServerTransport` instance.

Anthropic Messages API `tool_use_id`: based on `.claude/notes/07-multi-agent-caching.md` (the definitive project reference), the IDs are of form `toolu_01Abc...` — server-assigned, non-deterministic across calls. The canonicalization strategy in the design note is the authoritative spec for this project.

## Open questions

1. **Where exactly does `canonicalize_turn` get called?** The orchestrator module does not exist yet. E08_S04 creates `server/orchestrator/id_canon.py` as a pure utility (no caller in this milestone). The orchestrator that *calls* it is likely E08_S05's scope. The implementer should treat `id_canon.py` as a standalone library module with tests, not wired into anything else in this milestone.

2. **Does canonicalization produce a stable per-session mapping or is it positional?** The reference implementation in `07-multi-agent-caching.md:98-113` is positional — counter increments as IDs are encountered in order. The same Anthropic-supplied ID maps to the same canonical ID IF it appears at the same position. But if the same API-issued ID appears across two separate `canonicalize_turn` calls (e.g., two agents referencing the same tool call), the mapping is NOT stable unless the caller passes the same `id_map` dict across calls. The brief says the function takes `messages: list[dict]` with no state parameter — this implies it is called per-turn and is stateless between calls. **Implementer must decide**: stateless-per-call (positional within one call) vs. session-scoped (stable mapping across calls). The AC says "applying it twice produces the same result" — this only requires idempotency within one call, not cross-call stability.

3. **Where is `SessionState` stored?** The brief says "in a `SessionState` object keyed by `Mcp-Session-Id`." This is almost certainly an in-memory dict (`dict[str, SessionState]`) at the `server/session.py` module level, following the pattern from `server/cache.py` and `server/tools.py`. No persistence is mentioned; caps reset on server restart. TTL/eviction of dead sessions is unspecified — implementer should add a simple cleanup strategy (e.g., delete on `DELETE /mcp` terminate, or LRU eviction at 10K entries).

4. **`RETRIEVAL_CAP_REACHED` wire format?** The brief says "structured error with code `RETRIEVAL_CAP_REACHED` and a human-readable message." Two options in the current codebase: (a) raise `ValueError(...)` → FastMCP wraps to `isError=True` JSON-RPC error body; (b) return `CallToolResult(content=[TextContent(text=json.dumps({...}))], isError=True)` directly. Option (b) is richer (structured payload) and is the correct choice for a "structured error" as specified. Option (a) loses the `code` field. **Recommendation**: return `CallToolResult(isError=True, content=[TextContent(...)])` with the `structuredContent` carrying `{"code": "RETRIEVAL_CAP_REACHED", "message": "..."}`.

5. **Does the cap apply to attempted or successful calls?** AC: "A session that calls `search_papers` four times receives `RETRIEVAL_CAP_REACHED` on the fourth call." This means max 3 SUCCEED and the 4th ERRORS — the cap triggers on the 4th attempt. Counter increments should be checked BEFORE serving the call (guard at entry, not at exit). Similarly for `get_chunk` at 5 times (4 succeed, 5th errors).

   **FLAG**: The brief description says "maximum 3 retrieval rounds (calls to `search_papers`) and maximum 4 chunks materialized (calls to `get_chunk`)." But the AC says the 4th call to `search_papers` receives the error (cap is 3 successful calls) AND the 5th call to `get_chunk` receives the error (cap is 4 successful calls). These are consistent: cap=3 for search, cap=4 for chunk. The counter represents completed-calls count; on the Nth+1 attempt, error is returned without incrementing.

6. **Test file path: `server/orchestrator/test_id_canon.py` vs `tests/test_id_canon.py`?** The brief specifies `server/orchestrator/test_id_canon.py`. The project's `pytest.ini_options` has `testpaths = ["tests"]` — this file will NOT run in CI via plain `pytest`. The AC says "`pytest server/orchestrator/test_id_canon.py` passes" (explicit path), so it satisfies the AC when invoked directly. **Recommendation**: place it in `tests/test_id_canon.py` to match all other test files in this project and avoid CI gaps. If the brief is treated as authoritative on file location, add `server/orchestrator` to `testpaths` in `pyproject.toml`.

7. **How does middleware intercept tool calls per session?** FastMCP's `add_tool` does not pass session context to the handler. To enforce caps, the middleware must intercept at the ASGI layer (inspecting the MCP JSON-RPC method and params in the request body), OR the handler must receive the session-id somehow. The simplest approach: `server/middleware.py` adds a `SessionCapMiddleware` that reads `mcp-session-id` from headers and the `method` from the JSON-RPC body, intercepts `tools/call` for `search_papers` and `get_chunk`, checks and increments `SessionState`, and returns a `RETRIEVAL_CAP_REACHED` JSON-RPC response before forwarding to FastMCP. This is the correct pure-ASGI approach consistent with the existing middleware pattern.
