## Verified claim: m10's comment about which functions change

m10's own doc comment on `child_payload_root()` (main.rs:307-310) says: *"m7's onedir stages as a SIBLING of the supervisor executable. That is the convention m10 commits to and m15 replaces: once `.app` assembly lands, this parent chain becomes `Contents/MacOS` -> `Contents/Resources/...` and only this function changes."*

Read the full call chain to check this. `self_authored_plan()` (:334-353) calls `child_payload_root(supervisor_exe)` then `resolve_inside(&payload_root, &payload_root.join(child_executable_name()))`. `resolve_inside()` (:247-268) is generic path-containment logic with no baked-in assumption about sibling-vs-`Contents/Resources` layout — it just canonicalizes a root and a candidate and checks containment, refusing a symlinked root. **`child_payload_root()` is the only function whose BODY encodes the sibling-directory convention** (`supervisor_exe.parent().join(CHILD_PAYLOAD_DIR)`, :311-315). `resolve_inside()` needs no code change for a `.app`-relative root, only a different `root` argument computed by whatever replaces `child_payload_root()`. **The claim holds as one function's logic (`child_payload_root`) plus its caller passing a different root** — `resolve_inside()` itself is untouched, though the brief's own wording ("re-point `child_payload_root()` and `resolve_inside()`") is slightly imprecise: only the former's body changes; the latter is reused unmodified, exactly as m10's own comment (line 307-310) already predicts more precisely than the roadmap AC text.

`CHILD_PAYLOAD_DIR: &str = "arxmcp-desktop-child"` (:51) also needs to survive or be renamed depending on the chosen bundle layout — under `bundle.resources` or a `Contents/Resources` convention this constant becomes a subpath component, not necessarily the top-level sibling name.

## Tauri v2.11.5 bundle mechanics (this repo's exact pin)

Confirmed pins: `tauri = "=2.11.5"`, `tauri-build = "=2.6.3"` (`apps/desktop/Cargo.toml` workspace deps, cross-checked against `apps/desktop/Cargo.lock:3291-3293` and `:3343-3345` — lockfile matches the `=` pin exactly, no drift).

`tauri.conf.json` today has `"$schema": "https://schema.tauri.app/config/2"` (v2 config shape) and:
```json
"bundle": {
  "active": false,
  "icon": ["icons/icon.png"],
  "macOS": { "minimumSystemVersion": "14.0" }
}
```
No `resources`, no `externalBin`, no `macOS.frameworks`, no `resources` array. `build.rs` (5 lines) calls bare `tauri_build::build()` with no `tauri_build::Attributes`/`WindowsAttributes` builder — so today's `tauri-build` invocation reads `tauri.conf.json` at compile time but has nothing configured to embed. Turning `bundle.active` to `true` and adding either `bundle.resources` (a glob-to-path map copied verbatim into the bundle) or `bundle.externalBin` (a list of sidecar binary path prefixes, platform-suffixed, that `tauri-build`/`tauri bundler` copies alongside the main executable and that Tauri's runtime APIs can resolve via `resolve_resource`) is a `tauri.conf.json`-only change — no `build.rs` code addition is required for either mechanism as far as static config goes, based on reading the current build.rs and Cargo.toml (no `tauri-build` builder calls exist to extend). **This repo has never invoked the `tauri bundle`/`cargo tauri build` CLI mechanism at all — `bundle.active: false` means no `.app`, `.dmg`, or `.msi` has ever been produced by this codebase**, confirmed by the absence of any `tauri-cli` dependency in `Cargo.lock` (grepped; no `tauri-cli` entry) and no `dist/`/`bundle/` output directory anywhere under `apps/desktop/`.

Consequence for the ADR the milestone AC requires: this repo would be adopting the **first-ever use** of Tauri's bundler in this codebase, not extending an established pattern. The `tauri-cli` crate (or `cargo-tauri`) is not currently a dependency anywhere in the workspace and is a new toolchain dependency the ADR should name explicitly (it is the standard way to invoke `tauri bundle`; the alternative is scripting `tauri_build`'s lower-level bundler API directly, which the ADR should also weigh).

Per-OS consequence sketch (from Tauri v2's documented model, cross-referenced against what this repo's config already commits to):
- **macOS (`.app`)**: `bundle.resources` entries land under `Contents/Resources/`; `bundle.externalBin` entries land under `Contents/MacOS/` (sidecar convention, platform-triple-suffixed filename) — either would change `child_payload_root()`'s answer from "sibling of `Contents/MacOS/supervisor`" to "`Contents/Resources/<name>`" (resources) or "another entry directly inside `Contents/MacOS/`" (externalBin). `minimumSystemVersion` (already set to `14.0`) is consumed at `.app`/`Info.plist` generation time by exactly this bundler — confirming this key is otherwise inert with `bundle.active: false`.
- **Linux/Windows**: the roadmap's own "Supported boundary" language (README:42+) and CLAUDE.md's Windows-desktop-stack skip markers suggest the desktop distribution track is macOS-only in practice (`requires_desktop_package` is asserted macOS/Linux-only in CLAUDE.md §4.5, and `requires_desktop_stack`'s own macOS-only guards for `libomp`/Mach-O rewriting are pervasive) — but `tauri.conf.json` carries no OS-scoping today, so the ADR should state explicitly whether Linux/Windows bundle shapes are in scope for THIS milestone or deferred, since Tauri's bundler differs materially per OS (AppImage/deb vs `.app` vs NSIS/MSI) and the m7 PyInstaller onedir's `~0.75 GB` size class is a macOS/Linux-only build per CLAUDE.md.

## m7's onedir on-disk shape, and what embedding it costs the existing guards

No bundle currently exists on this box (`var/desktop-package/` absent — never built in this worktree), so the shape below is derived from the spec/driver source, not a live artifact listing. Per the spec (`arxmcp_desktop.spec:136-219`) and driver (`desktop_package.py:41-42,290-320`):

```
var/desktop-package/dist/arxmcp-desktop-child/      <- BUNDLE_NAME, distpath/BUNDLE_NAME
├── arxmcp-desktop-child                             <- CHILD_EXE (main entry, sys.executable == this)
├── arxmcp-desktop-probe                              <- PROBE_EXE (frozen latex2mathml parity probe, AC2)
└── _internal/                                        <- shared collected binaries+datas (both EXEs exclude_binaries=True, one COLLECT)
    ├── base_library.zip                               <- deterministically sorted (spec :30-41)
    ├── torch/lib/  (canonical OpenMP runtime, darwin+linux)
    ├── faiss/.dylibs/  (macOS only — dropped by m8's libomp consolidation before COLLECT, spec :98-119)
    └── ... (transformers, sentencepiece, latex2mathml, lancedb, kuzu, etc.)
```
Measured size class: "~0.75 GB per bundle" (CLAUDE.md §4.5, Makefile :103 echo). `desktop_package.py:40` sets `DEFAULT_ROOT = REPO_ROOT / "var" / "desktop-package"`, gitignored.

**What embedding does to each existing m7/m8 guard, mechanically:**
- **Determinism (AC1, `verify_determinism()` :662-721)** compares two builds' `file_manifest()` (mode:size:sha256 per relative path, :451-469). This is computed over the **onedir tree directly**, independent of any bundling step — embedding the onedir inside a `.app` via `bundle.resources`/`externalBin` is a copy operation the bundler performs after `desktop_package.py` finishes; it does not touch determinism of the onedir itself. What it DOES add: the bundler's own copy step (file timestamps, macOS resource forks/xattrs, ad-hoc re-signing of the whole `.app` if Tauri code-signs, `Info.plist` generation) could reintroduce nondeterminism at the bundle level that `verify_determinism()` never measures because it only ever inspected the onedir. **m15 needs an equivalent determinism check at the ASSEMBLED level**, or an explicit argument for why manifest-identity of the pre-bundle onedir plus a hash of the assembly step's own (already-deterministic) inputs is sufficient.
- **`direct_url.json` sanitization (AC4, `sanitize_direct_url()` :266-281)** runs on the **build venv's site-packages BEFORE `PyInstaller` even runs** (`build_once()` :633-634, before `build_bundle()`), so it is fully upstream of both the onedir and any later bundling step — bundling changes nothing here, confirmed by call-order reading. No re-run needed at the assembled level for THIS check's own logic, but the AC as m15 states it ("hold over the assembled artifact") should be read as "the property that was sanitized upstream must still be true when scanned downstream" — i.e. the build-root string scan (next bullet) is the actual re-verification vector, not this function.
- **Build-root string scan (`scan_tree()` :518-582, `default_needles()` :479-511)** byte-scans every regular file, `.zip` members, and (via `scan_embedded_archives()` :584-607) the PYZ archives inside both EXEs — for the operator's `$HOME`, `TMPDIR`, username, and repo/build/dist paths. This scan takes a `root: Path` argument and is fully generic over directory shape; re-running it with `root` = the assembled `.app`'s `Contents/Resources` (or wherever the payload lands) is a parameter change, not a rewrite, **provided the assembly step introduces no NEW build-machine-path-bearing files** (e.g. an `Info.plist` templated with an absolute build path, or a code-signing step embedding a build-host identifier) — the ADR/implementation should extend `default_needles()`'s `build_paths` tuple to include whatever path the assembler runs from, mirroring how `build_once()` already passes `(REPO_ROOT, work, dist)` (:642).
- **m8 single-`libomp` + weights-free guards (`_require_single_libomp()` :417-449, `libomp_inventory()` :389-414)** both take a `root: Path` and `rglob("*")` under it — same shape, re-pointable to the assembled artifact's payload root with a parameter change, PROVIDED the bundler does not itself introduce a second Mach-O copy of a dylib (Tauri's own dependencies, e.g. `webview2`/`WKWebView` linkage, are supervisor-side and outside `_internal/`, so should not collide with the Python closure's `libomp` — but this is an assumption to verify against a real build, not derivable from source alone).

## m9's `minos`/`minimumSystemVersion` agreement check — re-run scope

`tests/test_desktop_support_floor.py::TestBuiltArtifactDeclaresTheFloor` (:291-322) is parametrized over `_BINARY_ENV = ("DESKTOP_SUPERVISOR_BIN", "ARXMCP_FIXTURE_SIDECAR")` (:262) — **both are Rust binaries built by `cargo build`**, exported only by `desktop-conformance` (Makefile :161-176). Neither the PyInstaller `arxmcp-desktop-child`/`arxmcp-desktop-probe` executables nor an assembled `.app`'s `Contents/MacOS/supervisor` are read by this test today. Two separate things m15's AC5 could mean, and the ADR/implementation should disambiguate:
1. **Narrow reading** (what the existing test literally checks): the supervisor binary, once relinked/re-verified after being placed inside `Contents/MacOS/` of the assembled `.app`, still reports `minos 14.0` via `otool -l` — this is nearly free, since `.app` assembly does not recompile the Rust binary, only relocates/copies it; `otool -l` on the copy should be byte-identical to the pre-copy binary unless the bundler strips or re-signs it (re-signing does not change `LC_BUILD_VERSION`).
2. **Broader reading implied by the roadmap AC's "both binaries" phrase**: the PyInstaller-produced `arxmcp-desktop-child`/`arxmcp-desktop-probe` executables' OWN `minos`, which is determined by whatever CPython build `uv sync --python 3.12` resolves (`desktop_package.py::provision()` :207-263) — **no code anywhere pins or checks this today**; there is no equivalent to `.cargo/config.toml`'s `MACOSX_DEPLOYMENT_TARGET` for the Python build. If `uv`'s resolved CPython 3.12 build targets a lower macOS floor than 14.0 (plausible — a generic python.org/uv-managed interpreter build often targets an older minos for broad compatibility), the PyInstaller executables could legitimately disagree with the Rust binaries' declared floor, and nothing in the current test suite would catch it. **This is the single highest-value open question for m15's determinism/support-floor work** — it needs a live `otool -l` read of a built `arxmcp-desktop-child` executable to resolve, which this explore-role researcher did not build (no bundle was produced in this session; building one is ~150s+network per Makefile's own estimate and outside an explore role's no-mutation scope).

## Whether any committed gate builds both closures in one session

**Confirmed still true, independently re-verified from source** (matches m10 rectify summary's "What the fixes do NOT close" finding verbatim): `desktop-conformance` (Makefile :161-176) runs `cargo build --bin supervisor`/`--bin fixture-sidecar` and the Rust+Python test suites against those two binaries only — it never invokes `desktop_package.py`. `desktop-package`/`desktop-package-check` (Makefile :185-196) invoke `desktop_package.py build`/`verify` — pure Python/PyInstaller, never touches `cargo build` for the supervisor. `desktop-model-check` depends on `desktop-package` (Makefile :204, `desktop-model-check: desktop-package`) but still never builds the Rust supervisor. **No Makefile target, and no test file's fixture setup, combines a `cargo build --bin supervisor` with a `desktop_package.py build` run.** m15's AC ("`make desktop-package` (or a successor target) emits an artifact that launches by double-click... with `ARXMCP_DESKTOP_LAUNCH_PLAN` unset") therefore requires either a NEW Makefile target that runs both builds plus an assembly step, or extending one of the two existing targets to also invoke the other — this is new gate-authoring work, not a re-point of an existing one. Budget it: the PyInstaller build alone is ~150s+network-on-first-run (Makefile :101 echo) and the Rust build/test suite (`desktop-conformance`) has its own multi-minute cost (cargo fmt+test+clippy+2 builds+4 pytest invocations); a combined gate could plausibly run 5+ minutes and should be considered for `desktop-package-check`-style opt-in marker treatment (a `requires_desktop_launch` or similar new marker) rather than folding into `make test`'s default path, consistent with the project's existing precedent of keeping expensive desktop gates opt-in (CLAUDE.md §4.5's `requires_desktop_stack`/`requires_desktop_package`/`requires_bundled_model` markers all follow this pattern).

## Acceptance criteria the implementer must meet

1. Bundle mechanism (`bundle.resources` vs `bundle.externalBin` vs sibling-directory convention off `current_exe()`) chosen via a recorded ADR naming rejected alternatives and per-OS consequences — this is the **first use of Tauri's bundler in this codebase**, so the ADR has no local precedent to extend and should name the `tauri-cli`/`cargo tauri build` toolchain dependency explicitly.
2. `make desktop-package` (or a successor target) produces a double-click-launchable artifact reaching ready server + rendered window with `ARXMCP_DESKTOP_LAUNCH_PLAN` unset — requires a NEW combined gate; none exists today (see above).
3. `child_payload_root()` (main.rs :311-316) re-pointed at the bundle root; `resolve_inside()` (:247-268) is generic and needs no logic change, only a different `root` argument — re-assert both are exercised by a test, per m10's own scope note.
4. Frozen child inside the artifact byte-identical (hashed) to `make desktop-package`'s onedir output — `file_manifest()` (`desktop_package.py` :451-469) is the existing hashing primitive; reuse it against the assembled path.
5. m7's determinism/`direct_url.json`/build-root-scan and m8's single-`libomp`/weights-free guards re-run over the assembled artifact: `direct_url.json` sanitization is upstream and unaffected; the other four all take a `root: Path` parameter and are structurally re-pointable, contingent on the assembly step introducing no new leak surface (Info.plist templating, code-signing byproducts) — verify this against a real build, not by inspection alone.
6. `minos`/`minimumSystemVersion` agreement re-verified post-assembly — resolve whether "both binaries" means the two Rust binaries (near-free, `test_desktop_support_floor.py` already reads this shape) or the PyInstaller-produced Python executables (unpinned today, needs a live check of the `uv`-resolved CPython 3.12 build's own minos).
7. Artifact layout recorded in `apps/desktop/README.md`'s existing sections (:16-41 payload layout, :42+ supported boundary) — both already reference m15 by name and should be edited in place, not duplicated.

## Risks and open questions

1. **`bundle.resources` vs `externalBin` changes what "inside the bundle" structurally means for `child_payload_root()`** — `externalBin` places sidecars directly in `Contents/MacOS/` (same directory as `supervisor`, closest to today's sibling convention, smallest code delta); `bundle.resources` places them in `Contents/Resources/` (a different directory, requires `resolve_resource`-style path resolution at runtime, larger delta but more idiomatic for a non-executable-named-arbitrarily payload). This is the ADR's central decision and this researcher does not adjudicate it — but the size-of-delta asymmetry between the two options is a concrete input the ADR should weigh explicitly.
2. **No committed gate builds the Rust supervisor and the PyInstaller bundle together** — confirmed unchanged since m10. m15 must author this from scratch; budget it as new gate-authoring work (plausibly a new opt-in pytest marker following the `requires_desktop_package`/`requires_bundled_model` precedent), not a re-point of an existing target.
3. **The PyInstaller-produced executables' own `minos` is unpinned and unchecked anywhere in this repo** — unlike the Rust side (`.cargo/config.toml` `MACOSX_DEPLOYMENT_TARGET`), no equivalent env/build-flag pins the CPython/PyInstaller build's deployment target. This is a live risk to AC5/AC6 that needs a build-and-`otool -l` check to resolve, not resolvable from source reading alone.
4. **This is the first-ever invocation of Tauri's bundler/`tauri-cli` in this codebase** — `Cargo.lock` has no `tauri-cli` entry and no prior `.app`/`.dmg` output exists anywhere under `apps/desktop/`. Toolchain-onboarding risk (a new build-time dependency, potentially a new hash-pin surface) that the ADR should name, not just the resources-vs-externalBin choice.
5. **Assembly-step-introduced leak surface is unmeasured** — `Info.plist` generation, ad-hoc code-signing, and any timestamp/xattr normalization the Tauri bundler performs are new inputs to the m7 build-root scan and m8 libomp guards that this researcher could not exercise (explore role, no build performed). A live build is required before the re-pointed guards can be trusted to actually pass, not just to compile.
