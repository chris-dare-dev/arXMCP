# Adversarial research brief — desktop-distribution-m7

Role: `adversarial` (agent-b/c equivalent). Read-only. `.gitignore` was
observed unmodified relative to `HEAD` during this research window

## TL;DR

AC1 as written ("byte-identical manifests... excluding only files the
build tool itself declares non-deterministic, documented rather than
silently ignored") is achievable **only if "documented" is enforced as a
closed, reviewed allowlist with a test that fails on any NEW diverging
path** — left open-ended, it degrades exactly the way the milestone's own
framing warns about, because PyInstaller has at least four independent
non-determinism sources (embedded build timestamps in the bootloader,
`.pyc` `co_filename`/mtime, `zlib` archive member ordering, and absolute
paths compiled into some `.pyc` headers) with no single upstream flag that
suppresses all of them. Five of six ACs have a documented "cheap lie" path
already exemplified by precedent code IN THIS REPO (`test_probe_calls_freeze_support`
mocks the very call it should prove; `.venv`'s `direct_url.json` fix is a
single-file case that a scan can rubber-stamp on absence). The realistic
LOC estimate across the five closure criteria plus a genuinely
discriminating determinism test is 550–900 LOC, over the 800-LOC
soft-abort line the project's own pipeline reference sets
(`.claude/references/milestone-pipeline-phase-implement.md:19`) — it fits
as ONE milestone only if the determinism AC is narrowed up front, not
discovered mid-implementation.

## Attack 1 — Is "deterministic" achievable at all? (the load-bearing question)

**Verdict: not achievable as an unqualified claim; achievable as a scoped, closed-list claim with its own regression test.**

Concrete, known PyInstaller/CPython non-determinism sources, none refuted by anything measured in spike-1 (spike-1 never ran the build TWICE and diffed it — the only repeated-build evidence in the whole spike series is `tree_manifest` being used to prove **immutability of one artifact across a probe run**, i.e. "did this one build change while running", not "do two independent builds from the same source match"):

1. **`.pyc` invalidation headers.** CPython's default `.pyc` format embeds either `(source_mtime, source_size)` or a source hash, chosen by the compiler flags PyInstaller's `Analysis` step uses. Two builds run at different wall-clock times against the SAME on-disk source tree can still diverge if any intermediate step touches an mtime (e.g. `uv build`'s wheel extraction, or a `.pyc` regenerated during Analysis rather than reusing checked-in bytecode). This is testable without installing PyInstaller: `python -m compileall` twice against an unchanged tree and diff the `.pyc` bytes is a 30-second falsification the implementer should run FIRST, before spec-authoring, to know which invalidation mode to force.
2. **Archive/zip member ordering.** PyInstaller's `PYZ` (compressed Python archive) and the final `onedir` `_internal` layout are populated by iterating `Analysis`'s dependency graph, whose enumeration order can depend on filesystem readdir order (not guaranteed stable across two `os.walk` invocations on some filesystems, notably APFS with certain flags, though typically stable on a single unchanged tree — still unverified here).
3. **Bootloader binary.** PyInstaller ships a precompiled bootloader per platform; this part IS reproducible build-to-build (same binary, not recompiled), so it is NOT a real threat — but the code-signing step (ad-hoc, per spike-1) DOES embed a timestamp unless explicitly suppressed, and if signing becomes part of `make desktop-package` (the milestone brief doesn't exclude it — Blocker 4/signing is deferred, but nothing in the AC says the build step won't ad-hoc-sign), that's a fifth non-determinism source layered on top.
4. **`direct_url.json` and any other `dist-info` metadata carrying a wheel-build timestamp or path** — already independently required to be sanitized by AC4, so this one is at least addressed elsewhere, but the sanitization step itself must run BEFORE the manifest hash in AC1 is computed, or AC1 will always fail (a real interaction between two ACs the implementer must sequence correctly: hygiene passes first, then determinism check).

**What a meaningful determinism claim looks like instead of "byte-identical, exceptions documented":**
- A CLOSED, versioned exception list (a Python set or JSON file committed alongside the `.spec`), with a test asserting its exact size/contents don't silently grow.
- The claim scoped to "byte-identical **content-hash-relevant** manifest" — i.e. sort file paths + hash their *content* (already what `tree_manifest` does) while EXCLUDING files whose bytes are provably wall-clock-derived (the `.pyc` header bytes specifically, not the whole file — a smarter check could hash only the code object bytes past the header, which is more work but is the honest fix rather than excluding the whole file).
- Explicitly NOT claiming byte-identical bootloader-embedded timestamps or signature blocks if ad-hoc signing runs as part of `make desktop-package`.

If the exception list needs to include the `.pyc` header issue for a non-trivial fraction of the ~5,530 files spike-1 measured, "documented, not silently ignored" is still honest — but the milestone's own framing ("worse than one that never claimed it") is the right bar, and passing that bar requires the CLOSED-list-with-a-test design above, not the AC's current open phrasing.

## Attack 3 — Cost of two consecutive builds in the default gate

Measured baselines already in the repo (not this brief's estimate):
- Spike-1's SINGLE corrected build took **74.04 s** (`.claude/notes/spikes/desktop-distribution-spike-1.md:23`), producing 759 MB / 5,530 files. **Two independent builds** (the literal AC1 requirement) is therefore ≥148 s of build time alone, before hashing 759 MB × 2 (`tree_manifest` streams the file in 1 MiB chunks — CPU-bound SHA-256 over 1.5 GB is itself several more seconds, not free).
- `make desktop-conformance` currently runs `cargo fmt`, `cargo test --workspace`, `cargo clippy --all-targets --all-features`, two `cargo build` invocations, and three pytest suites (`Makefile:156-164`) — no committed timing figure exists in this tree for its current wall-clock cost (the CLAUDE.md test-count section only times `make test`, not `desktop-conformance` separately), so citing "~50s" from the dispatch prompt cannot be confirmed from source; treat it as unverified rather than repeating it as fact. What IS confirmed: `make test` alone was measured at **9m28s / 4447 tests** on 2026-08-01 (`CLAUDE.md:81-94`) — a two-build, 1.5 GB-hashing determinism check bolted onto that number, if placed in `make test`'s default path, would materially change that baseline and risks becoming the single slowest test in the suite by a wide margin.
- **This repo has a standing precedent AGAINST unmarked expensive desktop tests in `make test`**: the m6 critique caught exactly this (`.claude/notes/milestones/desktop-distribution-m6/findings.json:240`, "30 real process spawns... on any box with a built fixture-sidecar... 30-cycle stress" running unmarked) and the fix was retroactive `requires_desktop_stack` marking plus Makefile wiring into `desktop-conformance`'s explicit `-m` expression. m7's two-build determinism check, the 759 MB scan, and the frozen-bundle MathML/freeze_support subprocess launches are ALL at least as expensive as what m6 had to retrofit a marker onto — they should be born marked from commit one, wired into `desktop-conformance` (or a brand-new `make desktop-package-check` target, per the e4 research's own suggestion), never into bare `make test`.
- **Disk**: two full onedir builds (`--workpath`/`--distpath` pointed at distinct dirs, required to compare independently rather than overwrite-and-lose-the-first-build) is ~1.5 GB minimum, likely more with intermediate `build/` scratch retained by PyInstaller's own default `build/` output dir. Nothing in the milestone brief specifies cleanup. **A stray `build/` directory ALREADY exists untracked in this repo right now** (`git status --short` shows `?? build/`, containing `build/lib/**` and `build/bdist.macosx-11.0-arm64/` — clearly leftover `python -m build`/setuptools output, not committed, not in `.gitignore`). PyInstaller's OWN default `--workpath` is also `./build` — if the `.spec`/build script doesn't set an explicit, PyInstaller-specific `--workpath`/`--distpath`, its output will interleave with or overwrite this pre-existing unrelated `build/` directory, corrupting both. This is a concrete, present-tense collision risk the implementer must design around from the start, and plausibly part of why another session is touching `.gitignore` concurrently with this research (worth checking `.gitignore`'s current diff before implementation starts, without touching it here).
- **Flakiness prediction**: a two-build hash-compare test is the textbook shape of a flaky test on a shared, memory-pressured dev box (per this workspace's own `reference_mac_load_boot_storm_mcp_fanout` memory pattern) — two 74s+ builds run back-to-back under concurrent agent load easily hit swap, and PyInstaller's own dependency-walking step reads the filesystem non-atomically; a concurrent `uv sync` or unrelated agent editing the source tree mid-build (this workspace explicitly runs 2-3 concurrent sessions on `main`, per `CLAUDE.md:100-103`) would make the two builds NOT be from "the same commit" in spirit even if `git rev-parse HEAD` reports one, because uncommitted working-tree drift between the two build invocations is exactly the kind of divergence AC1 doesn't account for. The implementer should snapshot/verify a clean `git status` before EACH of the two builds, not just once before the pair.

## Attack 4 — The PyInstaller dependency trap

**Argument: ephemeral provisioning is the worse failure for THIS project's stated values, but a locked dependency is the worse failure for THIS project's existing precedent — and the honest middle is a THIRD option neither extreme in the brief considers.**

- **Locked project dependency** (`pyproject.toml` `dev` extra or a new `desktop` extra): PyInstaller + `pyinstaller-hooks-contrib` are dev/build-only tools with their OWN dependency footprint (PyInstaller alone pulls in `altgraph`, `pefile`/`macholib` depending on platform). Added to `[project.optional-dependencies].dev` (currently just `ruff` + `pytest`, `pyproject.toml:321-324`), this doesn't ship in the runtime wheel (dev extras never do) — so the "leaks into the runtime wheel" risk from the attack prompt is actually LOW, contradicting the framing that this is automatically bad. The real risk is narrower: it changes `uv.lock`'s resolved set and gives CI/every-clone a new heavy(ish) dependency to resolve on every `uv sync --extra dev`, and — per attack point 3's finding above — makes AC1's determinism claim ONLY as strong as the exact PyInstaller/hooks-contrib version pin, which a lockfile-based install DOES provide. This is consistent with how the project already handles `ruff`/`pytest`.
- **Ephemeral provisioning** (installed into a throwaway venv at build time, not locked): this is the pattern the project uses for MinerU (`pyproject.toml:325-333`, explicitly to avoid MinerU's transformers-v4 cap polluting the pinned stack) — a real, working precedent for "heavy/risky tool stays OUT of the lockfile, pointed at via an env var" (`ARXMCP_MINERU_BIN`). Applying the same pattern here (`ARXMCP_PYINSTALLER_VENV` or similar) keeps `uv.lock` clean but means the EXACT PyInstaller/hooks-contrib version used for any given build is only pinned by convention/documentation, not by the lockfile — directly undercutting AC1's determinism claim, since "deterministic build" implicitly requires "deterministic toolchain," and an unpinned ephemeral install is one `pip install pyinstaller` (latest) away from a silently different build.
- **The honest middle, not named in either extreme**: pin PyInstaller + `pyinstaller-hooks-contrib` to EXACT versions (mirroring how `pyproject.toml` per-line-comments its other deps) in a NEW, narrowly-scoped optional extra (e.g. `[project.optional-dependencies].desktop-build = [...]`) — separate from `dev` so a plain `uv sync --extra dev` (what most agent sessions run per `CLAUDE.md:234-239`) does NOT pull it in, but `make desktop-package` can `uv sync --extra desktop-build` on demand. This gets lockfile-verifiable determinism (closes AC1's real gap) without polluting the default dev environment's resolution graph or every session's `uv sync` cost, and without the MinerU-precedent's "version drift by convention" weakness. This should be flagged to the implementer explicitly, since neither of the brief's own two framings (`locked` vs `ephemeral`) is actually what the project's existing pattern space supports best.

## Attack 6 — Invariants m7 could break

- **`make wheel-check`'s 191-entry / package-data expectation** (`tests/test_wheel_packaging.py`, derived from `pyproject.toml`'s `[tool.setuptools.package-data]` glob list): m7 should NOT touch `pyproject.toml`'s packaging section for the RUNTIME wheel at all — PyInstaller build tooling belongs in a new optional extra (Attack 4), not in `packages.find`/`package-data`. ## Determinism verdict (repeated, standalone, per required output shape)

**AC1 as literally written is not honest.** "Byte-identical... excluding only files the build tool itself declares non-deterministic, documented rather than silently ignored" invites an open-ended, ever-growing exception list, because PyInstaller does not have a single authoritative "these files are non-deterministic" declaration mechanism to defer to — the implementer would be the one deciding what counts as "the build tool declares," which is indistinguishable from silently choosing what to exclude.

**What should replace it:** a CLOSED, versioned, size-pinned exception set (not a prose list) covering ONLY the specific, structurally-understood non-determinism source(s) actually measured on this toolchain (starting hypothesis: `.pyc` header bytes only, verifiable in 30 seconds via a double `compileall` diff before any PyInstaller work begins), with:
1. A regression test asserting the exception set's exact size/membership, so it cannot silently grow.
2. The manifest hash computed over file CONTENT with the known-nondeterministic byte ranges stripped, where feasible (e.g. skip the `.pyc` header's 16 bytes, hash the rest) — rather than excluding whole files, which hides real content drift inside an "expected diff" file.
3. An explicit non-claim alongside it: this proves reproducibility of THIS commit on THIS host/toolchain-version pair, not cross-machine or cross-PyInstaller-version reproducibility — matching the "Not proven on Intel" / "Not proven under a cold cache" honesty pattern the e4 brief already applies to its own claims.

If the two-build harness, after being built honestly, finds MORE non-determinism than the `.pyc`-header hypothesis accounts for (e.g. real archive-ordering drift), that is a genuine, reportable finding for the implementer to surface — not a reason to widen the exception list ad hoc without re-justifying it in the same commit.
