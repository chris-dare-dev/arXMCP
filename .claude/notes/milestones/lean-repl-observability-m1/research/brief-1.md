### 1. `server/lean_repl.py` — harness

- **Imports (31-56):** `time` is NOT currently imported — add `import time`. The POSIX-only `resource` import-guard pattern at 48-51 (`try/except ImportError`) is a nearby precedent for defensive imports but is not needed here (`time` is stdlib, cross-platform).
- **`__init__` (111-139):** THIS is where both new fields must be initialized, NOT `spawn()`. Reason: `generation` (an existing per-instance field, 133-135) is set here with a default (`generation if generation is not None else secrets.token_hex(8)`) specifically so the fake-process construction path in tests needs no signature change (`self._io_lock = asyncio.Lock()` at 139 is the last line of `__init__`). `tests/test_lean_repl.py:178-180`'s `_repl(proc)` helper calls `LeanRepl(proc, Path("fake_lake"), Path("fake_repl_dir"))` directly — 3 positional args, bypassing `spawn()` entirely. Every test in `TestFakeProcRoundTrips` (183-253) goes through this helper. If spawn-time / counter init lived in `spawn()` instead of `__init__`, all of `TestFakeProcRoundTrips` would get a REPL with no spawn time / stuck-at-default counter. Mirror the `generation` pattern exactly: plain instance attributes set unconditionally in `__init__`, e.g. `self._spawn_monotonic = time.monotonic()` and `self._env_snapshot_count = 0`.
- **`spawn()` classmethod (145-251)** and **`spawn_from_config()` (253-272):** no change needed — they just call `cls(proc, lake, rd)` / `cls.spawn(...)`, which already routes through `__init__`.
- **`is_running` (278-281) / `generation` (283-293) properties:** the exact pattern to mirror for the 2 new read-only properties (e.g. `env_snapshot_count -> int`, `age_seconds -> float`). `age_seconds` should be computed on every access (`time.monotonic() - self._spawn_monotonic`), not cached — same idiom as the existing `is_running` property reading `self._proc.returncode` live.
- **`query()` (295-329):** the whole method body already runs under `async with self._io_lock:` (311). The increment belongs INSIDE that block, after `_round_trip` succeeds and before `return`. Concretely, restructure the `try/except TimeoutError` so the success path does something like `resp = await asyncio.wait_for(self._round_trip(command), timeout=timeout); self._env_snapshot_count += 1; return resp` — i.e. the increment must NOT run on the `LeanReplTimeoutError` path, nor on the pre-check `LeanReplError` raised at 312-316 for an already-exited process, nor on any `LeanReplError` `_round_trip` itself raises (EOF at 351-355, non-JSON at 377-382) — all of those are exception paths that skip past a post-success increment naturally. Because `_io_lock` already serializes every `query()` call (docstring at 27-28 of the module: "One REPL process, one stdin/stdout stream: serialise round-trips so two concurrent queries cannot interleave their JSON on the wire"), a plain `+= 1` under that same lock is race-free — **no new lock/primitive is needed**.
- **`_round_trip()` (331-382):** no change — stays protocol-agnostic (still just JSON in/out).
- **`close()` (388-432):** no change. Confirmed: a respawn is a brand-new `LeanRepl(...)` object (see `server/handlers/lean_verify.py:954-957` below) — a fresh instance naturally starts `_env_snapshot_count = 0` and `_spawn_monotonic = time.monotonic()` (now), which is exactly the "gauge drops toward 0 on respawn" behavior AC2 wants. `close()` itself does not need to reset anything.
- **`__all__` (435-441):** no new names need exporting unless the implementer wants the properties documented there (they're instance properties, not module names — likely no change).

### 2. `server/metrics.py` — gauge pattern to copy

- **Module docstring naming convention (10-13):** `arxmcp_<subsystem>_<metric>_total` for counters, `arxmcp_<subsystem>_<metric>` for gauges — the brief's two names already conform (`arxmcp_lean_repl_env_snapshots`, `arxmcp_lean_repl_age_seconds`).

We use `arxmcp_latexml_drift_fixtures` here to avoid the collision."* Not directly relevant to a name collision for this milestone (no existing `arxmcp_lean_repl_*_total` counter to collide with), but it's the file's own citation for the gauge-vs-counter naming discipline the brief references.

- **`refresh_cache_metrics(cache: RetrievalCache | None)` (332-353)** is the function shape to mirror for `refresh_lean_repl_metrics(lean_repl: LeanRepl | None) -> None`. **Important divergence — see Risk 1 below**: `refresh_cache_metrics` NO-OPS on `cache is None` (documented at 340-341: "the gauges retain their last observed value"). - **`reset_cache_metrics_for_tests()` (369-383)** is the reset-helper template; `_reset_child()` (356-366) is only needed for labeled Counters/Gauges with per-label cells — since the new gauges are unlabeled, a plain `GAUGE.set(0)` per gauge suffices (no `_reset_child` needed), mirroring `reset_sentinel_metrics_for_tests` (412-424) rather than `reset_cache_metrics_for_tests`.
- **`__all__` (427-453):** add the 2-3 new gauge names + `refresh_lean_repl_metrics` + `reset_lean_repl_metrics_for_tests`.
- **No delta-tracking needed.** `EMBED_SINGLEFLIGHT_DEDUP_COUNTER` (a `Counter`, `server/health.py:162-173`) needs the module-level `_LAST_DEDUP_COUNT` delta-tracker (187-591) BECAUSE Prometheus `Counter`s must only ever increase by the true delta since the last scrape. The new lean_repl metrics are `Gauge`s — a direct `.set(lean_repl.env_snapshot_count)` / `.set(lean_repl.age_seconds)` at every scrape is correct and sufficient, exactly like `CACHE_BYTES_GAUGE` / `refresh_cache_metrics`. Do not copy the Counter-delta pattern here.

## Risks and open questions

1. **AC3's "reads 0" requirement conflicts with the `refresh_cache_metrics` no-op-on-`None` convention.** `refresh_cache_metrics` (`server/metrics.py:332-353`) deliberately leaves gauges at their "last observed value" when its singleton is `None` (documented behavior, fine for cache bytes which only matters once warm). Prometheus `Gauge`s are module-level and persist for the whole pytest process (`tests/test_server_metrics.py:129-132`), so if a prior test in the same session set `arxmcp_lean_repl_env_snapshots` to a nonzero value, a bare no-op on `lean_repl is None` would leave it nonzero and fail AC3's disabled-path test. Use the explicit-zero convention instead (`refresh_sentinel_metrics` / `refresh_degraded_mode_metric` in `server/health.py`), and make sure `reset_lean_repl_metrics_for_tests()` is added to the `reset_all_metrics` fixture (`tests/test_server_metrics.py:125-146`).
2. **Proxy choice — round-trip counter vs. max env/proofState id.** The brief explicitly frames this as an open choice. Recommendation: the simple round-trip counter (increment once per successful `LeanRepl.query()` call, regardless of `cmd`/`tactic_step` shape). Evidence for this being (almost) exactly as tight as the "max id" alternative: `.claude/docs/lean-sandbox-design.md:71-74` states the REPL's own `recordCommandSnapshot` appends on **every** command — "a `def`, a failed `theorem`, even a read-only `#check` advances the counter" — so in normal (non-adversarial-token) operation, one successful `query()` call ⇔ exactly one new array entry. The one divergence: a response shaped `{"message": "Unknown environment."/"Unknown proof state."}` (`server/handlers/lean_verify.py:363-366`, `409-423`) is successfully JSON-round-tripped (no exception in `LeanRepl.query`) but likely does NOT grow the REPL's array (the id lookup fails before recording) — so the round-trip counter would over-count by exactly 1 in that edge case. That case is adversarial/buggy-caller-only (a legitimate caller only ever replays an `env`/`proofState` int the REPL itself returned), and over-counting is the safe direction for a resource-growth gauge. The "max id observed" alternative would need `LeanRepl.query()` to peek at `resp.get("env")` / `resp.get("proofState")` — two extra `.get()` calls, mild but real protocol-knowledge creep into an otherwise protocol-agnostic harness (`_round_trip`, 331-382, currently has zero awareness of Lean-specific field names) — and would need to combine two SEPARATE arrays' maxima into the ONE unlabeled gauge the brief names, which the round-trip counter does for free (both `cmd` and `tactic_step` calls go through the same `query()` method, so one integer already unifies both).
3. **`tests/test_handlers_lean_verify.py`'s `_FakeLeanRepl` will NOT gain the new properties, and does not need to.** Confirmed by tracing both singleton paths: `server/main.py:469` (`app.state.resources = resources`) and `:482` (`set_resources(resources)`) assign the SAME object in production, but `tests/test_handlers_lean_verify.py:107-126`'s `_attach_fake_resources` only calls `set_resources(fake)` on a hand-rolled `_FakeResources`/`_FakeLeanRepl` pair and never builds a FastAPI app / hits `/metrics` — so `refresh_lean_repl_metrics` is never invoked against that fake in the existing suite. No update to that file is required by this milestone; do not feel obligated to retrofit `_FakeLeanRepl` with the new properties.
4. **The optional RSS gauge should likely be deferred.** `psutil` is NOT in `pyproject.toml` dependencies (checked directly), the brief forbids adding it as a hard dependency, and there is no existing RSS-reading code anywhere in the repo (no `/proc` reader, no `ctypes`/`GetProcessMemoryInfo` Windows reader) to reuse. The dev/CI-equivalent host for this repo is Windows (this session's own platform, and CLAUDE.md's whole "win32-portability push" section) — a from-scratch Windows RSS reader (ctypes + `psapi.dll`) would be new, untested surface for a milestone explicitly scoped as "S (~1 day)". The brief's own escape hatch ("otherwise omit and record it as a deferred sub-item") is the recommended path; the count + age gauges alone satisfy AC1-3 and AC6-7.
5. **Increment placement must exclude every exception path, not just the timeout.** `LeanRepl.query()` (295-329) has 3 distinct ways to NOT return a value: the pre-check raise at 312-316 (process already exited), the `LeanReplTimeoutError` translation at 321-329, and whatever `_round_trip` itself raises (EOF at 351-355, non-JSON at 377-382 — note `_round_trip` is called from inside `query`'s `try`, so its raises also propagate through the `except TimeoutError` guard untouched, i.e. as generic `LeanReplError`, not caught/reclassified there). The increment must sit strictly after `_round_trip` returns and before `query` returns — placing it in a `finally` block, or before the `await`, would incorrectly count failed round-trips.
