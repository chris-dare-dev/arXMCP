# `search_papers` snippet contract

This document is the single authoritative specification for the
`search_papers` tool's result-row shape, frozen at E06_S04. The
machine-readable JSON Schema lives at
[`server/schemas/search_papers_result.json`](../server/schemas/search_papers_result.json);
this page is the human-readable summary plus the architectural
intent behind four explicit decisions.

## (a) Snippet is 150 characters max — no LLM rewriting

Every result row carries a single inline text field, `snippet`:
the first **150 characters** of the chunk's canonical body text
(column `body_text` in the LanceDB chunks table; conceptually
`body_canonical` per design note `04-parsing-and-chunking.md`).
The truncation is a byte-for-byte slice — no ellipsis added, no
LLM rewriting, no paraphrasing.

Rationale: agents triage relevance from the snippet alone; if the
candidate is interesting they call `get_chunk(chunk_id)` for the
full body. The 150-char cap is small enough to fit ~50 results
under the 256 KB inline-payload cap (E06_S01) yet large enough to
expose a theorem statement's lead clause.

## (b) No `summary` field — permanently dropped

Earlier design drafts proposed a `summary` field per result, to be
generated by a Haiku call at search time. **This field is
permanently dropped.** Three reasons:

1. **BP1 byte-stability.** The summarizer prompt is application
   code; bumping its version invalidates every cached
   `tools/list` and `search_papers` response (per
   `.claude/notes/07-multi-agent-caching.md`). The `summary`
   field would silently invalidate the entire prompt cache on
   any prompt edit.
2. **Duplication with snippet.** A 150-char snippet from the
   chunk body is already a relevance signal. A Haiku-rewritten
   summary either says the same thing differently (waste) or
   says different things (relevance noise the agent must
   reconcile).
3. **`get_chunk` exists.** Agents that need the full body call
   `get_chunk(chunk_id)`. There is no use case where a Haiku
   summary beats the full body once an agent has decided the
   chunk is worth examining.

The `tests/test_snippet_contract.py::test_no_summary_field` test
locks this — a regression that re-introduces `summary` fails
loudly.

## (c) No dependency on Anthropic Citations API

The arXMCP design is **explicitly decoupled from Anthropic's
Citations API**. The Citations API validates document blocks in
the Messages API request body (`messages[].content[]`); it does
NOT process MCP tool results. Wiring tool results through
Citations API blocks is architecturally unsound:

- It would couple the MCP server to a client-side Anthropic API
  feature that other MCP clients (Claude Desktop, Cursor, custom
  clients) cannot guarantee.
- It would require the server to know the client's Citations
  configuration, which the MCP protocol does not expose.
- It would break the spec-correct dual-mode design described in
  section (d) below.

Agents that need provenance attribution call
`get_chunk(chunk_id)` to retrieve the full body with metadata
(`paper_id`, `theorem_label`, `section_path`, `body_text`), then
assemble citations themselves from those fields. The agent
runtime (E08) is the right layer to orchestrate this; the MCP
server stays agnostic.

## (d) `resource_link` content blocks alongside `structuredContent`

The MCP 2025-06-18 spec's `CallToolResult` carries TWO
output channels:

- `structuredContent`: a JSON object the agent reads
  programmatically. The frozen shape is in
  [`search_papers_result.json`](../server/schemas/search_papers_result.json).
- `content`: an array of content blocks the agent or client may
  display. v1 emits:
  - `content[0]`: a `TextContent` with the JSON-pretty-print of
    `structuredContent` (preserves the FastMCP default for
    clients that read `content[0].text`).
  - `content[1..N]`: one `ResourceLink` block per result row,
    in the same `(score_desc, chunk_id_asc)` order, with
    `uri = arxmcp://chunks/<chunk_id>`. Spec-compliant clients
    may follow these to fetch chunks.

The `resource_link` blocks are **advisory**. The agent runtime
(E08) does NOT depend on the client following them — it relies
on the agent explicitly calling `get_chunk(chunk_id)`. This
dual-mode design is intentional:

- MCP-spec-compliant clients (resource-aware UIs) get the
  resource link surface for free.
- Agents that ignore `content` and read only `structuredContent`
  still work correctly via the explicit `get_chunk` path.

Neither path requires the Citations API.

## How to fetch the full body

When an agent decides a search result is worth examining:

```python
# 1. Search for relevant chunks.
results = await search_papers(query="Riemann-Roch theorem")

# 2. Pick a chunk and fetch its full body.
top = results["structuredContent"]["results"][0]
full = await get_chunk(chunk_id=top["chunk_id"])

# 3. Assemble citation from `full["chunk"]["paper_id"]` etc.
```

This pattern is uniform across MCP clients and does not depend
on any client-side API beyond MCP itself.

## Out of scope

- LLM-generated summaries (permanently dropped — see section b).
- Anthropic Citations API integration (permanently dropped — see
  section c).
- ColBERT-based snippet extraction (deferred to v1.5; v1's
  byte-prefix slice is the contract).
